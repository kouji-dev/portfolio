Six agents, one repo, zero merge hell

Running coding agents in parallel on one codebase: a worktree each, owned files, and a merge queue that keeps main green.

DN
Driss NajihJul 2026 · 5 min read

Give one coding agent a task and it works like a careful colleague: it reads, edits, runs the tests. Give six of them the same repository and they behave like six people sharing one laptop.

The problem#

They overwrite each other's files, run the tests against half-finished changes, and the last one to finish inherits everyone's conflicts.1 Adding a seventh makes it faster worse.

The fix is not a smarter agent. It is the discipline a human team already uses: separate checkouts, clear ownership, and one gate into main. None of it is new; CI systems and merge queues have done it for people for years. Agents just make the problem arrive in an afternoon instead of a quarter.

Plain git all the way

Every step here uses git and a test runner. Orrery automates the same steps, but nothing in this post depends on it.

One worktree per agent#

A git worktree is a second checkout of the same repository, on its own branch, sharing one object store. It takes seconds, and it means an agent's half-written file never exists in another agent's tree.

Six of them, in whichever shell you use:

  1. Create each worktree from the current main.
  2. Install dependencies once per worktree.
  3. Start each agent with its working directory set to its own worktree.
  4. Remove the worktree once its branch has merged: git worktree remove ../agent-1.

Share the package store, not node_modules

pnpm links every worktree to one content-addressed store on disk, so six installs mostly cost links, not downloads.

Owned files#

Worktrees stop agents from seeing each other's unfinished work. They do not stop two agents from editing the same file and colliding at merge time. That takes a plan made before anyone starts: every task names the paths it may change.

Watch the lockfile

It is the file every task wants to touch. Give it to one agent; the others ask for a dependency instead of adding it.

A merge queue#

Six branches finishing at different times is where the trouble usually starts. Instead of merging as they finish, each finished branch joins a queue. The queue takes one at a time, rebases it on the current main, runs the gates, and merges only if they pass.

On GitHub the same queue is a branch protection setting, and CI listens for it:2

Never force-push main to unblock the queue

Revert the bad merge with a new commit instead. Every worktree was made from main; rewriting it pulls the floor from under all six.

What it changed#

6agents working at once
1repository, one main
0conflicts allowed to reach main

Conflicts still happen. They happen earlier, on one branch, in one worktree, to the one agent that knows what it was doing, instead of on main at the end of the day in front of a person.

Conflicts still happen. They just happen to one branch at a time.

Why not let each agent open a pull request?

You can, and the queue still applies: a pull request is how a branch asks to join it. What matters is that nothing merges outside the queue.

Why rebase instead of merging main into the branch?

A rebased branch merges fast-forward, so the history of main stays one line and every step on it was tested exactly as it landed.

What if the gates are slow?

Test two or three queued branches together and split the batch only when it fails.

Takeaways#

  • Isolate. One worktree and one branch per agent; nobody shares a working tree.
  • Assign. Every path has one owner before work starts, the lockfile included.
  • Queue. One way into main: rebased, tested, fast-forward.
  • Stop cleanly. An agent stopped with Ctrl + C leaves its worktree as it was; nothing else is touched.
